# 要件と保証範囲

Moletta は、明確な成果を目指す AI 開発において、能力の見落とし、未知の方式の未探索、部分試験の過剰な一般化、局所最適化を減らすためのハーネスです。主担当 AI が作業の選択と最終判断を担います。

## 契約

| ID | 要件 | 実現する責務 | 確認する層 |
| --- | --- | --- | --- |
| R1 | 人の原文、目的、必須制約を維持する。分解と実現方法は更新できる | 技能の要求抽出、封印した意図と可変計画 | runtime の改変・対応検査、原文レビュー |
| R2 | 開始状態から成功状態までの必要能力と、その実現手段を確認する | 探索・比較、案ごとの能力対応 | 構造検査と、意味上の欠落を扱う行動評価 |
| R3 | 知っている技術だけで選ばず、異なる仕組みと適用条件を調べる | 一次資料の調査、根拠と推論の区別 | 出典対応検査、未知方式の行動ケース |
| R4 | 全工程で成果へ届く構成を比較し、重要な未知と再考条件を残す | 主担当の比較、条件付き判断 | 判断状態の検査、全体処理の行動ケース |
| R5 | 判断を変える実験を、範囲・環境・保持／省略条件・対照付きで設計する | 可変計画、実行前の観測開始 | 実験の対応検査と実物の意味判断 |
| R6 | コマンドとホスト操作の実際の観測を保存し、対象と実験に結び付ける | 共通の観測ライフサイクル | CLI、状態遷移、ハッシュ、対象変更のテスト |
| R7 | 部分・別環境の成功を全体達成に読み替えず、失敗を保持する | 判定履歴と readiness の導出 | 適用範囲、否定結果の解消、全経路のテスト |
| R8 | 小変更には相応の手順を使い、重要な作業は予算を決めて再開できる | 入口の分岐、次の行動、checkpoint | 実行ツールと小変更の行動ケース |
| R9 | 実際の失敗から狭い改善仮説を作り、効果と過剰手順を比較する | 改善技能、評価パケット、独立採点と比較 | 評価器の検査と、同条件の baseline／candidate 実行 |
| R10 | Codex と Claude Code で同一の技能を使い、成果物だけで現在仕様を理解できる | プロジェクト導入、Claude プラグイン、文書と共通検証入口 | 導入・配布・参照検査、各ホストでの行動確認 |

## 要求と仮説の境界

全案共通の要求は、人の成果と制約から導く観測可能な能力です。たとえば「再接続後に正しい結果へ収束する」は共通要求にできます。「キャッシュを無効化する」はキャッシュを持つ案の設計上の義務であり、キャッシュを使わない案の必須条件にはしません。方式固有の義務は、その案の仕組み・実験に置きます。

明示要求には原文の引用を付け、導出要求には推論であることを示します。原文から独立した文脈で必要能力を再構成するレビューを使い、引用があるだけで抽出が完全だとは扱いません。分解を見直す場合は理由を残し、人の目的・必須制約を維持します。

## 保証の境界

- 型、参照、対応、保存ファイルの整合性はローカルツールが検査します。意味上の要求の欠落、技術資料の妥当性、観測の因果関係は AI または人が判断します。
- 直接実行したコマンドと、ホストの実際の操作履歴を取り込む観測は取得元を区別します。どちらも、意図的な記録の捏造を防ぐ認証サービスではありません。
- 明示した入力ファイルの変更を検出します。外部製品の版や、列挙されていない依存関係の同一性までは検証しません。
- 構造上の検証準備が整っても、自動で「意味上の成功」「全体最適」「判断精度の改善」とは宣言しません。
- 人にしか分からない選好・許容損失・目的変更は人が決めます。通常の調査、実装、検証には既存の権限を使います。
