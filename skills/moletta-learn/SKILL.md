# Moletta Learn

元の目的・制約、実行記録、実物を読み、失敗の観測と原因仮説を分ける。単発事例から一般則を作らず、技能の変更が課題に必要か判断する。

## 限定した変更候補

1. 何を満たせなかったか、どの判断で外れたか、元の指示や証拠から何が分かったかを残す。実装・知識・指示・評価の不備を区別する。
2. 「この条件ではこの観測を先に確かめる」のように適用条件を狭くした改善仮説を作る。不要な段階、レビュー、試作を全作業へ追加しない。
3. 最小の変更候補、効果を観測できる回帰例、過剰適用を検出する例を用意する。永続的な教訓や共有設定へ自動で追記しない。変更は認められた範囲に提案し、評価済みでも外部反映の権限は別に守る。

## 行動を評価する

- 基準版と候補版に同じ公開ケースを与え、実際の成果物と判断を比較する。評価者用の採点基準・期待する見落としは公開ケースと分離する。
- 独立した文脈の実行者へ渡すのはケースの依頼、技能、必要な生の資料のみ。疑う失敗、期待回答、採点基準を混ぜない。[delegation.md](../moletta/references/delegation.md) を参照する。
- 回帰例だけでなく、改善に使わなかったケースでも評価する。必要な能力の見落とし、誤った完了宣言、偽の測定などの重大失敗は、平均点が向上しても昇格を止める。
- 成功率に加えて費用、往復回数、時間、不要な質問・レビューなどの誤検出を比較する。同一条件をそろえられない差は限界として残す。
- runtime の単体・CLI テストや frontmatter 検査は構造検査であり、エージェントの判断改善を実証する行動評価ではない。

## 採用または差し戻し

証拠が改善を支持する範囲だけを採用候補とし、評価結果、残る懸念、戻す条件を記す。重大失敗、効果不明、過剰適用があれば修正を狭めるか戻す。評価環境がなければ未検証の提案として渡し、実証済みと呼ばない。
