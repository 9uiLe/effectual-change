# Outcome Harness

元の依頼から「何が実現すれば成功か」と人が指定した必須制約を保ち、次に不確実性を減らす行動を選ぶ。分解、実装方法、採用案は証拠に応じて作り直せる。

## 最初の分岐

- **狭く、低リスクで、成功条件が明確**: 原文と制約を確認し、必要な変更と相応の実物確認を行う。複数案、複数試作、独立レビュー、実行記録一式を一律には要求しない。新しい不確実性が判断を左右すると判明したら通常経路へ移る。
- **目的への道筋が不確か、案の選択が重要、複数回にまたがる**: [workflow.md](references/workflow.md) を読み、原文・意図・可変の作業記録を分けて開始または再開する。

全技能を順番に読み込まない。現在の未解決事項に必要なものだけ使う。

| 未解決事項 | 読む技能 |
| --- | --- |
| 要求、実現方式、試すべき問いが不明 | [outcome-explore](../outcome-explore/SKILL.md) |
| 全体としてどの案を選べるか | [outcome-compare](../outcome-compare/SKILL.md) |
| 実物が目的と要求を満たすか | [outcome-verify](../outcome-verify/SKILL.md) |
| 再発する失敗から手順を改善するか | [outcome-learn](../outcome-learn/SKILL.md) |

## 維持する区別

- **人の目的・必須制約**と**こちらが導いた分解・仮説**を分ける。局所最適化で全体が届かないなら、分解や全体構成まで戻す。制約を緩めて帳尻を合わせない。
- **調べれば分かる事実**は資料、既存物、実験で調べる。人にしか分からない事実は具体的な不足として尋ねる。価値の優先順位、許容する損失、目的の変更を代わりに決めない。各工程の承認待ちを作らず、既に認められた範囲を進める。
- **資料にあること、測れたこと、推論したこと**を分ける。部分試験、別環境、終了コード 0 を全体達成に読み替えない。
- 構造検査はリンク・記録・証拠ファイルを検査する。要求の意味上の抜け、根拠の妥当性、最適性をすべて検出できない。原文と実物を読む判断を省略しない。

委譲・独立レビューが有益なら [delegation.md](references/delegation.md)、設計の背景と適用限界を調べるなら [sources.md](references/sources.md) を読む。すべての sibling skill は同時に導入し、相対参照を保つ。
