# 意思決定ループ

## 目的と適用範囲

**入力：** おおむね明確な変更要求 + 不完全に理解された既存実装。

**目標：** 要求を満たし、既存システムの守るべき振る舞いを維持する変更に到達すること。設計経路は状況に応じて更新できるが、要求そのものをAIが無断で変更してはならない。

**対象：** 機能追加、バグ修正、性能改善、条件付き表示、アーキテクチャ移行。

## 5原則を用いた反復

1. **手中の鳥 — 現状を把握する。** 変更対象のソース、テスト、実際の動作、依存、既存のパターンを調査する。発見は「観測事実」「仮説」「合意済み要件」「未確認」に分け、根拠（ファイル位置、実行ログ、画面、担当者の回答など）を結びつける。
2. **許容可能な損失 — 変更の境界を決める。** 変更不可の振る舞い、回帰リスク、時間・費用の上限、試行環境、停止・切り戻し条件を明確にする。
3. **レモネード — 最小の検証を選ぶ。** 不確実性が重要な判断を妨げる場合だけ、調査・計測・小さな実装・比較実験を行う。予想外の事実が出たら仮説を更新する。
4. **クレイジーキルト — 必要な合意を得る。** 実動作、スクリーンショット、動画、計測や差分を提示し、AIには決められない仕様・UX・許容範囲について担当者に判断してもらう。合意内容を受け入れ条件に変える。
5. **飛行機のパイロット — 制御可能な実装へ収束する。** 現時点の要件に必要な変更を、テスト可能性・保守性・監視・切り戻し能力を損なわない範囲で確定する。過剰な将来予測に基づく抽象化は避ける。

この順番は説明上の便宜であり、実行順序の強制ではない。新しい制約を見つけたら調査に戻り、人間の合意が必要になったら確認する。

## 「次の行動」を決める規則

現時点で最も重要な未知・リスクを一つ特定し、次の規則で行動を選ぶ。

| 状態 | 優先する次の行動 |
| --- | --- |
| 対象コードや現在の振る舞いがわからない | 追加調査・再現 |
| 目標達成を左右する仮説が未検証 | 最小の実験・計測 |
| 要件の正当性やUXに人間の判断が必要 | 担当者への確認 |
| 既存契約やデータを壊すおそれがある | 作業を止め、境界と復旧策を再確認 |
| 想定外の発見で前提が変わった | 設計候補・判断記録を更新 |
| 重要な不確実性が解消され、検証手段がある | 最小限の実装を行う |
| 受け入れ条件と回帰検証を満たした | 変更を確定・報告 |

複数の選択肢がある場合は、**意思決定に重要な不確実性を、許容損失内で最も効率よく減らせる行動**を優先する。調査や候補比較は無制限に続けない。

## 確実性のラベル

- **観測事実（Observed）：** コード、テスト、計測、再現可能な動作から確認したこと。根拠を記録する。
- **仮説（Inferred）：** それらから推測したが、検証できていないこと。
- **合意済み要件（Confirmed）：** 権限を持つ担当者との明示的な合意や確定済み仕様。
- **未確認（Unknown）：** 現状では情報が不足していること。

「観測事実」は「望ましい仕様」と同義ではない。変更前の振る舞いがバグである可能性も考える。

## 完了条件

- 変更要求に対する受け入れ条件が確認されている。
- 主要な仕様と互換性リスクに対する検証結果がある。
- 必要な担当者合意を得ている。
- 既知の残余リスク・未確認事項が報告されている。
- 実装の差分が、目標に対して過不足ないことを説明できる。

> **安全上の原則：** 人間の承認が必要な事項をAIが推測で代替しない。非可逆・本番データ影響・セキュリティに関わる変更は、該当する既存のレビューと承認プロセスを守る。

## 記録方法

重要な判断やリスクがある変更では [意思決定記録テンプレート](../assets/change-decision.md) を使い、「何がわかっていたか」「なぜ次の行動を選んだか」「何で検証したか」を残す。軽微な変更に過剰な記録を強制しない。
