# Maintaining Moletta

- Treat `docs/requirements.md` as the current product contract. Preserve user outcomes and hard constraints; decompositions and mechanisms remain revisable hypotheses.
- Skills own decision policy, runtime owns typed records and observation integrity, evaluation owns packet/judgment contracts, distribution owns host placement. Keep dependencies in the directions described in `docs/architecture.md`.
- Keep the entry skill small and read focused guidance only when needed. Check the path from starting state through necessary operations to observable results on every route; keep narrow, low-risk work short. Choose structured records for resumption, repeated experiments or evidence applicability, not importance alone.
- Helper storage needs an initialized RUN, not a sealed design or full verification plan. Always clean up owned devices and distinguish helper success from product verification. Respect actual consent and host capabilities; use the reservation ledger only when needed.
- Change public CLI/data contracts, calling skills, examples and tests together. Do not preserve unspecified APIs, aliases or data formats with compatibility paths.
- Tests express observable guarantees at the smallest suitable boundary. Test-generated judgments are synthetic fixtures, never efficacy evidence.
- Never describe structural readiness as semantic completeness, authentic observations, global optimality or improved decisions. Keep evaluator rubrics out of solver packets. The evaluator's promotion gate requires fresh private transfer evidence for behavioral-improvement claims; assess bounded maintenance or equal-quality efficiency changes on their own evidence while retaining case regressions and critical failures.
- Validate with `python3 scripts/validate.py`. Preserve LICENSE and Git history. Write current specifications without conversation-dependent change narratives.
