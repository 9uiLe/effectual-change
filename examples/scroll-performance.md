# 事例：スクロールのカクツキを改善する

> これは架空の適用例。実測データや改善結果ではない。

## 変更要求
「この画面のスクロールがカクツクので改善したい」

## 不確実性
性能低下の原因は事前に断定できない。レイアウト、描画、データ処理、画像読み込み、不要な再描画など、複数の可能性がある。

## 5原則を使った判断

**手中の鳥**
- 対象画面と再現手順、利用端末・OS・データ量を確認する。
- 計測ツールと、再利用できる既存のパフォーマンステストを把握する。
- ボトルネックの原因を計測前に決めつけない。

**許容可能な損失**
- 表示される内容、操作、アクセシビリティを原則として維持する。
- 一つの変更の効果を比較できる大きさで実験する。
- 失敗時に容易に戻せる変更から試す。

**レモネード**
- 計測結果が仮説と異なる場合は、原因仮説を更新する。
- 例えば、描画を疑っていたがデータ変換がボトルネックなら、最初のUIリファクタリング案を中止する。
- 発見と再現手順を残す。

**クレイジーキルト**
- 変更前後の動画、同等条件での計測値、知覚的な違いを担当者と確認する。
- スムーズさとトレードオフになる見た目・操作感の変更は、責任者の判断を得る。

**飛行機のパイロット**
- 今計測できたボトルネックへの対処を優先する。
- 将来のあらゆる画面の最適化を目的とした基盤刷新は、必要性がなければ行わない。
- 再測定可能なテスト・トレース条件を維持する。

## 検証の例
- 同一端末・同一データ・同一手順で変更前後を測る。
- フレーム時間・ジャンク発生率など、対象環境で適切な指標を選ぶ。
- 平均値だけではなく悪い側の分布も見る。
- UIの機能・視覚的な仕様が変わっていないか確認する。

## 次の行動の分岐
| 状態 | 次の行動 |
| --- | --- |
| 再現できない | 条件を追加調査する |
| 原因が不明 | トレースと計測を行う |
| 原因の仮説が複数ある | 最も小さく切り分けられる実験を選ぶ |
| 数値は改善したが見た目が変化した | 担当者に確認する |
| 効果が確認でき回帰もない | 変更を確定する |
